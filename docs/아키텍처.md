# 아키텍처

`CLAUDE.md`의 요약을 더 자세히 풀어놓은 문서. 코드를 고치기 전에 훑어보면 좋다.

## 구조

```
app/
  main.py     FastAPI 라우트 (/api/jobs CRUD, /api/search 작품 검색, /api/library 뷰어 조회,
              /api/online/* 온라인 보기, zip/이미지 서빙, 정적 파일)
  jobs.py     인메모리 작업 레지스트리 + 백그라운드 실행 (Job 클래스, run_job) — 다운로드 전용
  crawler.py  실제 크롤링/다운로드/압축/검색 로직 (원본 스크립트를 함수 단위로 정리).
              get_episode_list/get_image_list/search_titles는 부작용 없는 순수 조회
              함수라 online.py도 재사용한다 — crawl_toon/download_image/zip_directory만
              "다운로드"(파일을 씀) 전용.
  online.py   온라인 보기 탭 전용 — 파일을 전혀 쓰지 않는 읽기 전용 실시간 조회
              (crawler의 조회 함수를 감싸기만 함). jobs.py/crawl_toon과는 무관.
  library.py  downloads/ 를 읽기 전용으로 스캔해 뷰어용 작품/회차/이미지 목록을 만듦
  models.py   pydantic 요청/응답 모델 (CrawlJobRequest, JobStatus)
static/
  index.html, style.css, app.js   바닐라 JS SPA (프레임워크 없음).
                                   "다운로드" 탭은 2초 폴링, "뷰어"/"온라인 보기" 탭은 진입 시 조회.
docs/
  USAGE.md            사용자용 사용법 문서
  VIEWER_FEATURES.md  뷰어 세부 기능(검색·정렬, 이어보기/읽음, 웹툰/페이지 넘김 모드,
                      읽는 방향, 전체화면) 설명
  CHANGELOG.md        이 앱(FastAPI 웹 버전)에 추가된 기능들의 변경 이력
  아키텍처.md         (이 문서)
  design.md           UI가 따르는 디자인 시스템 원본(참조용, Binance 스타일 다크+옐로 토큰)
  개선사항.md         브라우저 접근 없이 코드 트레이스로 찾은 버그/개선 아이디어와 처리 상태
downloads/    실행 시 생성되는 다운로드 결과물 (gitignore 대상). 뷰어가 읽는 소스이기도 하다.
cwraling_download_manga_img_site2.py   원본 단일 파일 스크립트 (참고용으로 보존, 더는 유지보수 대상 아님)
```

## 아키텍처 핵심

- **작업(Job) 상태는 프로세스 메모리에만 존재**한다 (`app/jobs.py`의 `_JOBS` dict).
  서버 재시작 시 작업 목록/로그는 사라진다. 다중 워커/다중 프로세스 배포는 지원하지
  않는다 — 로컬 1인 사용을 전제로 한 설계.
- 크롤링은 `requests` + `BeautifulSoup` 기반의 블로킹 I/O이므로, `BackgroundTasks`를
  통해 FastAPI 기본 스레드풀에서 실행한다(`jobs.run_job`). asyncio 이벤트 루프에서
  직접 돌리지 않는다.
- 프런트엔드는 상태를 서버에 밀어넣지 않고 `GET /api/jobs`를 2초마다 폴링해서
  다시 그리는 방식이다(`static/app.js`). 실시간성이 중요해지면 WebSocket/SSE로
  바꿀 여지가 있지만 현재는 폴링으로 충분히 단순하다.
- 원본 스크립트는 압축에 로컬 설치된 Bandizip(`subprocess`)을 호출했다. 웹 서버
  환경에서는 이식성이 없으므로 표준 라이브러리 `zipfile`로 교체했다(`crawler.zip_directory`).
- 원본 스크립트의 이미지 다운로드 실패 처리는 **무한 재귀 재시도**였다. 스택 오버플로
  위험이 있어 `crawler.download_image`에서 `MAX_DOWNLOAD_RETRIES`(5회) 제한을 두고
  실패를 로그로 남기도록 바꿨다.
- **`/api/search`는 브라우저가 대상 사이트를 직접 호출하지 못해서 있는 프록시다**
  (다른 오리진으로의 요청이라 CORS에 막힘). 서버가 대신
  `crawler.search_titles`를 호출해 결과를 그대로 돌려준다 — 서버 쪽에 검색
  결과를 저장/캐싱하지 않는다, 매 요청마다 대상 사이트를 다시 호출. 프런트엔드
  (`static/app.js`의 `runTitleSearch`/`renderSearchResults`)는 결과를 클릭하면
  다운로드 폼의 작품 ID·제목 칸만 채울 뿐, 검색과 다운로드 작업 생성은
  완전히 분리된 별도 동작이다.
- **뷰어(`app/library.py`)는 DB가 없다.** `downloads/` 디렉터리를 요청마다 그대로
  `os.listdir`로 스캔해서 응답을 만든다. 개인 로컬 라이브러리 규모(수십~수백 작품)에는
  충분하지만, 작품 수가 아주 많아지면 매 요청마다 디스크를 훑는 비용이 커질 수 있다 —
  그때는 결과 캐싱을 고려.
- `separate_folders=False`로 받은 "평면" 다운로드(`downloads/{title}/001_001.jpg`
  형태, 폴더 없이 파일명 앞자리 3자리 숫자가 회차 번호)도 뷰어가 회차 단위로 보이도록
  파일명 접두사를 정규식(`FLAT_PREFIX_RE`)으로 재그룹핑한다. 이 명명 규칙은
  `crawler.crawl_toon`의 `file_prefix = f"{episode_num:03d}"`와 짝을 이루므로,
  둘 중 하나를 바꾸면 다른 쪽도 맞춰야 한다.
- `/files`는 `downloads/` 전체를 읽기 전용 `StaticFiles`로 그대로 서빙한다(경로 탈출은
  Starlette가 막아준다). `/api/library*` 쪽 경로 파라미터(`title`, `episode_id`)는
  추가로 `library._safe_join`을 거쳐 `downloads/` 밖으로 나가지 못하게 이중 검증한다.
- **읽기 진행 상태(이어보기/읽음 표시)는 서버에 전혀 저장되지 않는다.** 전부
  `static/app.js`의 `localStorage`(`mangadl_progress_v1` 키, 작품별
  `{lastEpisodeId, lastImageIndex, scrollY, readEpisodeIds[], updatedAt}`)에만
  있다. 브라우저/기기 간 동기화가 필요해지면 그때 서버 저장(DB든 JSON 파일이든)으로
  옮겨야 한다. 온라인 보기 탭에는 이 진행 상태 저장 자체가 없다(다운로드 안 한
  콘텐츠를 "내 라이브러리"처럼 취급할 이유가 약해서 의도적으로 뺐다).
- 리더의 연속 스크롤(자동 다음 화 로드)은 `IntersectionObserver` 두 개로 돌아간다:
  스트립 맨 끝의 sentinel 엘리먼트를 보는 `sentinelObserver`(다음 회차를 미리
  가져와 이어붙임)와, 각 이미지에 걸어 두는 `positionObserver`(화면 중앙 근처를
  지나는 이미지를 찾아 현재 페이지 표시·헤더 갱신·읽음 처리·진행 상태 저장을
  한 번에 처리). 새 회차를 이어붙일 때마다 그 회차의 `<img>`들만 추가로
  `observe()`하고, 옛 sentinel은 `unobserve` 후 제거한다 — 이 관찰자 쌍을 건드릴
  땐 두 옵저버가 서로 다른 역할(로드 트리거 vs. 위치 추적)이라는 점을 유지해야 한다.
- 자동 다음 화 로드는 **앞으로만** 동작한다(뒤로 이어붙이는 무한 스크롤은 없음).
  "이전 화" 버튼은 항상 새로 fetch해서 스트립을 그 회차 하나로 리셋한다.
- 리더는 **보기 모드가 두 가지**다: `readerRuntime.viewMode`가 `"scroll"`(웹툰,
  위 항목의 연속 스크롤)이면 `#reader-strip`을, `"paged"`(페이지 넘김)이면
  `#reader-pager`(1쪽 또는 2쪽 스프레드 + 좌우 클릭 존, `renderPagedImage`가
  매번 통째로 다시 그림)를 보여준다. 두 모드 모두 헤더 등 같은 리더 셸
  (`renderReaderShell`)을 한 번만 만들고 재사용하며, 셸을 다시 그리지 않고
  body만 갈아끼운다 — `toggleViewMode`/`pagerStep`/`gotoRelativeEpisode`가
  `openEpisodeScroll` 또는 `openEpisodePaged`만 직접 호출하는 이유. 모드·읽는
  방향(`readerRuntime.direction`, LTR/RTL)·1쪽/2쪽 여부
  (`readerRuntime.paged.pagesPerView`)는 각각 `localStorage`
  (`mangadl_reader_view_mode`, `mangadl_reader_direction`,
  `mangadl_reader_pages_per_view`)에 저장되어 다음 리더 진입 시에도 유지된다.
- 검색창(`#viewer-search`)은 화면 하나뿐이지만 **컨텍스트에 따라 검색 대상이
  바뀐다**: `viewerState.view === "episodes"`이면 회차명을 걸러 `renderEpisodeGrid`를
  다시 그리고, 그 외(titles)면 작품명을 걸러 `renderTitleGrid`를 다시 그린다
  (`titleSearchQuery` vs `episodeSearchQuery`, 화면 전환 시마다 초기화). 정렬
  드롭다운(`#viewer-sort`)은 회차 화면에서 의미가 없어 `hidden`으로 숨긴다.
- 페이지 넘김 모드는 스크롤 모드의 `IntersectionObserver` 인프라를 전혀 쓰지
  않는다 — `readerRuntime.paged`(현재 회차 이미지 배열 + 인덱스)만으로 상태를
  관리하며, 회차 경계를 앞뒤 양방향으로 자유롭게 넘나든다(`pagerStep`). 스크롤
  모드의 자동 로드가 앞으로만 되는 것과 달리, 페이지 넘김은 "이전 화"로 넘어가면
  그 회차의 마지막 쪽을 즉시 fetch해서 보여준다.
- **2쪽(스프레드) 보기의 `index`는 항상 쌍의 앞쪽(먼저 나오는) 페이지를
  가리키는 짝수 정렬 인덱스**다(`alignToPairStart`). `readerRuntime.direction`은
  그 쌍을 화면 왼쪽/오른쪽 어디에 그릴지만 결정할 뿐 `index`가 가리키는 페이지
  자체는 바꾸지 않는다 — 진행 상태 저장(`lastImageIndex`)이 방향 설정과 무관하게
  일관되게 유지되는 이유다. `pagerStep`/`jumpToPage`/`openEpisodePaged`가
  `index`를 바꾸는 모든 지점에서 2쪽 모드일 때는 반드시 이 정렬을 다시 적용한다.
- **전체화면(몰입 모드)은 실제 Fullscreen API**(`requestFullscreen`/
  `exitFullscreen`)를 쓴다. `body.immersive` 클래스는 버튼 클릭이 아니라
  `fullscreenchange`(+`webkitfullscreenchange`) 이벤트 하나로만 켜고 끈다
  (`syncImmersiveWithFullscreen`) — 그래야 `Esc`로 브라우저가 직접 전체화면을
  끝냈을 때도 UI가 어긋나지 않는다. 리더를 벗어날 때(`showTitles`/`openTitle`)
  `exitFullscreenIfActive()`로 명시적으로 전체화면을 종료시킨다.
- **`hidden` 속성을 쓰는 요소에는 그 요소(또는 그 클래스)에 `display`를 직접
  지정하는 author CSS 규칙을 두지 말 것.** `[hidden] { display: none }`은
  브라우저 기본(UA) 스타일시트 규칙이라, specificity와 무관하게 author
  스타일시트의 `display` 선언(`.btn { display: inline-flex }`,
  `.viewer-controls { display: flex }`, `.reader-strip { display: flex }` 등)이
  origin 우선순위로 그냥 이겨버린다 — `el.hidden = true`를 줘도 실제로는 안
  숨겨져서 웹툰/페이지 넘김 스트립이 겹쳐 보이거나, "숨긴" 검색창이 계속
  보이는 식의 버그가 났었다. `style.css` 최상단의
  `[hidden] { display: none !important; }` 한 줄로 전역 해결했다 — 새 토글
  가능 요소를 추가할 때 이 규칙에 기대면 되고, 별도의 `.xxx-hidden` 클래스를
  또 만들 필요는 없다.
- **온라인 보기 탭(`static/app.js` 맨 아래, `onlineState`/`onlineReaderRuntime`
  이하)은 뷰어 탭 코드와 상태를 전혀 공유하지 않는다** — 함수 이름도 전부
  `online` 접두사(`openOnlineEpisode`, `renderOnlinePagedImage` 등)이고, DOM id도
  전부 `online-` 접두사(`#online-reader-strip` vs `#reader-strip`)라 두 리더가
  같은 페이지에 동시에 존재해도 절대 충돌하지 않는다. 의도적으로 뷰어 탭의
  리더 로직(연속 스크롤·페이지 넘김·observer 두 개 조합)을 그대로 복붙 수준으로
  다시 구현했다 — 이미 여러 번 고친 뷰어 탭 코드를 온라인 보기 때문에 다시
  건드려서 회귀를 낼 위험을 피하려는 선택이다. CSS 클래스(`.reader-header`,
  `.reader-strip`, `.reader-pager`, `.page-zone`, `.chapter-divider` 등)와
  전체화면 로직(`toggleImmersive`/`exitFullscreenIfActive`/
  `syncImmersiveWithFullscreen`, 순수 Fullscreen API 래퍼라 상태가 없음),
  보기모드·방향·1·2쪽 설정의 `localStorage` 키(`READER_VIEW_MODE_KEY` 등),
  `alignToPairStart`/`cssEscape`/`escapeHtml`/`escapeAttr`는 상태 없는
  유틸리티라 그대로 공유한다. 새 DOM 참조 상수(`onlineBody`,
  `onlineBreadcrumb` 등)를 추가하면서 선언을 빼먹는 실수를 한 번 했다(런타임
  `ReferenceError`) — 실제 사용 전에는 안 잡히는 종류의 버그라, 새 함수에서
  전역 DOM 참조를 쓰기 전에 그 참조가 실제로 `const ... = document.getElementById(...)`
  로 선언돼 있는지 항상 확인할 것.
- 다운로드 탭의 작품 검색 결과 목록(`#search-results`)도 같은 종류의 실수가
  있었다: CSS는 `.search-results` 클래스를 대상으로 간격/스크롤 제한을
  정의했는데, 정작 컨테이너 엘리먼트에 그 클래스가 붙어 있지 않아서 스타일이
  전혀 적용되지 않고 있었다(마크업에 `class="search-results"`를 추가해서 수정).
  `innerHTML`로 내용만 갈아끼우는 컨테이너는 클래스를 static HTML 쪽에 미리
  박아두는 편이 이런 실수를 줄인다 — JS 쪽에서 매번 클래스를 다시 넣어줄 필요가
  없기 때문.
- **온라인 보기 회차 목록은 사이트가 주는 순서(보통 최신순)를 그대로 쓰지만,
  "다음/이전 화" 탐색은 배열 인덱스와 반대 방향**이다 — `gotoOnlineRelativeEpisode`,
  `onOnlineReachEnd`, `onlinePagerStep`, `updateOnlineReaderChrome`이 전부
  `idx - 1`을 "다음 화", `idx + 1`을 "이전 화"로 취급한다(처음엔 반대로
  구현했다가 버그로 발견 — 뷰어 탭의 로컬 회차 목록은 다운로드 시점에
  오래된순으로 이미 재배열돼 있어 `idx + 1` = 다음 화가 맞지만, 온라인 보기는
  사이트 원본 순서를 그대로 쓰기 때문에 방향이 반대다). 이 네 함수 중
  하나만 고치고 나머지를 안 맞추면 다시 거꾸로 동작하니 함께 수정해야 한다.
- **탭을 전환해도 `viewerState.view`/`onlineState.view`는 리셋되지 않는다** —
  리더를 연 채로 다른 탭으로 이동해도 그 상태는 `"reader"`로 남아있다(리더
  DOM도 그대로 살아있어 "그 탭으로 돌아오면 읽던 자리 그대로 보인다"는 동작을
  의도적으로 유지하기 위함). 대신 두 리더의 `keydown` 리스너는 각각
  `if (state.view !== "reader" || panel.hidden) return;`처럼 **패널이 실제로
  보이는지**도 함께 확인한다 — 이 `.hidden` 체크가 없으면 로컬 리더를 연 채
  탭만 바꿔 온라인 리더를 열었을 때 두 리스너가 한 키 입력에 동시에 반응하는
  버그가 난다(직접 겪음). 새로운 전역 `keydown`/`click` 같은 리스너를 추가할
  땐 `state.view` 체크만으로 충분하다고 가정하지 말 것.

## 사이트 종속성 (중요)

`app/crawler.py`는 특정 게시판 CMS 구조를 그대로 가정한다:

- 목록: `{site_url}/bbs/board.php?bo_table=toons&is={toon_id}&page={n}`,
  `button.episode.is-series` 안의 `div.episode-title.ellipsis` + `onclick`의
  `wr_id=` 파싱.
- 상세: `{site_url}/bbs/board.php?bo_table=toons&stx=GTO&is={toon_id}&wr_id={id}`,
  `<script>` 태그 안 `var img_list = [...]` JS 배열 파싱.
- 검색: `{site_url}/bbs/ajax.search.php?search_key={query}` — 사이트 자체
  검색창(입력할 때마다 실시간 자동완성)이 호출하는 것과 동일한 비공식 내부
  엔드포인트다. `curl`로 사이트 홈을 받아 인라인 `<script>`를 읽어서
  알아냈다(공식 문서 없음). 응답 JSON은 `bo_table=toons`와 `bo_table=cartoonson`
  두 게시판 결과가 섞여 오고, `counts` 필드가 그 경계(앞쪽 `counts`개가
  `toons`)다. `crawler.search_titles`는 **`counts` 경계를 넘는 항목(=
  cartoonson)을 조용히 버린다** — 이 크롤러가 `toons` 게시판만 지원하기
  때문. 사이트가 이 엔드포인트나 응답 구조를 바꾸면(비공식 API라 예고 없이
  바뀔 수 있음) 검색만 조용히 깨지고 다운로드 자체는 영향받지 않는다.

다른 사이트 구조를 지원하려면 이 함수들(`get_episode_list`, `get_image_list`,
`search_titles`)을 새 사이트의 HTML/API 구조에 맞게 고쳐야 한다 — 범용
크롤러가 아니다. 이 세 함수는 부작용 없는 순수 조회라 `crawl_toon`(다운로드)과
`online.py`(온라인 보기) 양쪽에서 재사용된다 — 다만 `crawl_toon`은
`get_episode_list` 결과를 페이지별로 뒤집어서 전체적으로 오래된 순서로
번호를 매기고, `online.py.list_episodes`는 뒤집지 않고 사이트가 주는 순서
(보통 최신순) 그대로 돌려준다는 차이가 있다 — 이 차이 때문에 위
"아키텍처 핵심"의 온라인 보기 방향 관련 항목이 존재한다.
